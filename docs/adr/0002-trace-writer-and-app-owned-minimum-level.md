# TRACE-level Writer and the application-owned minimum logging level

The Writer hands an entry to the logging framework at TRACE, which is what upstream Logbook does and what the extension keeps. Quarkus lets an extension own the level of a log category through `LogCategoryBuildItem`, which is also the only place the extension can ask for a category minimum level: Quarkus turns that item into the runtime level default and into a minimum level default, and without the latter it promotes the category to DEBUG and swallows every entry. That is not enough in a built application. There every `LoggerNode` carries an immutable minimum level that the logging framework fixes at startup from the `logging.initial-configurator.min-level` property, and Quarkus computes that property at build time from the build time logging configuration — the root minimum level, lowered by any category minimum level the application declares. An extension cannot contribute to that configuration: it produces build items, runtime configuration defaults and system properties that are only applied once the application has already started, and all of those arrive too late. So the floor an extension leaves for its own category is the root minimum level, and the extension cannot lower it. Rejected: having the extension emit the same `logging.initial-configurator.min-level` system property Quarkus already emits — the winner between two items with the same key depends on build step order, and it would move the floor of every category in every application that pulls the extension in. Rejected: writing at DEBUG or INFO to stay above the floor — DEBUG is filtered by the default INFO handlers a built application installs, and INFO would put every Exchange in front of applications that never asked for HTTP logging.

Consequences: the extension owns only the category level and its minimum level default, so an application that wants Exchanges in a built application must set the build time `quarkus.log.category."org.zalando.logbook".min-level` to TRACE and let its log handlers accept TRACE (`quarkus.log.console.level`, `quarkus.log.file.level`). The integration-tests application sets all three, which is why its built application logs Exchanges while a bare one does not; see its `application.properties`.
